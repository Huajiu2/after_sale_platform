## 二、主流程：售后工单完整生命周期

### 2.1 流程概述

一张售后工单从创建到终态，经历以下 5 个阶段：

```
 ① 提交申请 ──> ② 限流校验 ──> ③ MQ投递 ──> ④ AI审核 ──> ⑤ 终态
                                                           ├── AI已办结
                                                           ├── 已驳回（AI直接驳回）
                                                           ├── 待人工审核 ──> 人工同意
                                                           │               └── 人工驳回
                                                           └── 已关闭
```

### 2.2 各步骤详细说明

#### 阶段①：用户提交售后申请

| 步骤 | 操作 | 涉及组件 |
|---|---|---|
| 1.1 | 用户填写订单号、售后类型、原因、上传凭证图片 | 前端页面 |
| 1.2 | 前端表单校验（必填项、图片格式和大小） | 前端 |
| 1.3 | 调用后端 `/api/after-sale/submit` 接口 | HTTP |

#### 阶段②：限流校验与缓存穿透防护

| 步骤 | 操作 | 涉及组件 |
|---|---|---|
| 2.1 | Redis 布隆过滤器检查订单号是否存在（防缓存穿透） | Redis |
| 2.2 | Redis 令牌桶检查用户是否超出限流配额 `rate:limit:token_bucket:{userId}` | Redis |
| 2.3 | 校验通过，扣减令牌，继续处理 | Redis |

**限流逻辑伪代码：**

```java
// 1. 布隆过滤器：拦截恶意订单号
if (!bloomFilter.mightContain(orderNo)) {
    throw new BizException("订单号不存在");
}

// 2. 令牌桶限流：从系统配置读取容量和速率
Config config = systemConfigService.getByGroup("redis");
int capacity = config.getInt("rate_limit.token_bucket_capacity");
int refillRate = config.getInt("rate_limit.max_requests_per_min");

// Redis LUA 脚本原子执行
String key = "rate:limit:token_bucket:" + userId;
boolean allowed = rateLimiter.tryAcquire(key, capacity, refillRate);
if (!allowed) {
    throw new BizException("提交过于频繁，请稍后再试");
}
```

#### 阶段③：数据库写入与 MQ 投递

| 步骤 | 操作 | 涉及组件 |
|---|---|---|
| 3.1 | 生成工单号 `SH + yyyyMMdd + 3位序列` | MySQL |
| 3.2 | 写入 `after_sale_order` 表，初始 `ticket_status=0`（待AI审核） | MySQL |
| 3.3 | 写缓存：工单基本信息入 Redis，TTL 600s | Redis |
| 3.4 | 更新 Redis ZSet 店铺售后计数 `ZINCRBY rank:store:monthly:202606 {storeId} 1` | Redis |
| 3.5 | 按售后类型确定路由键，投递 MQ 消息到对应队列 | RabbitMQ |
| 3.6 | 返回前端：**「售后申请提交成功，AI审核中」** | HTTP |

**MQ 消息路由规则：**

| 售后类型 | 路由键 | 目标队列 |
|---|---|---|
| 1-仅退款 | `refund.only.created` | `queue.refund.only` |
| 2-退货退款 | `refund.return.created` | `queue.refund.return` |
| 3-投诉 | `complaint.created` | `queue.complaint` |

#### 阶段④：AI 智能审核（详见子流程②）

消费者消费消息后执行 RAG 检索 + LLM 裁决，将结果写回工单。

#### 阶段⑤：终态处理

| 结果 | 工单状态 | 后续操作 |
|---|---|---|
| AI 判定通过/驳回且置信度 ≥ 阈值 | `ticket_status=1` AI已办结 | 更新 Redis 统计、记录审计日志 |
| AI 判定「待人工」或置信度 < 阈值 | `ticket_status=2` 待人工审核 | 发送延迟催单消息（24h后触发） |
| 人工审核同意 | `ticket_status=1` 已办结 | 优质判例入库 |
| 人工审核驳回 | `ticket_status=3` 已驳回 | 优质判例入库 |
| 用户或系统关闭 | `ticket_status=4` 已关闭 | 无需操作 |

## 四、子流程②：AI 智能审核（RAG + LLM）

这是项目的核心亮点，结合了 RAG 检索增强生成与 LangChain4j 大模型调用。

### 4.1 整体架构

```
                    ┌──────────────────────────────────────────────┐
                    │              AI 审核消费者                     │
                    │                                              │
  MQ消息 ──>  消费   │  ┌──────────┐    ┌──────────┐    ┌────────┐  │
               消息   │  │ RAG检索   │───>│ 构建Prompt │───>│ LLM裁决 │  │
                    │  │ PgVector  │    │LangChain4j│    │Ollama  │  │
                    │  └──────────┘    └──────────┘    └────┬───┘  │
                    │                                       │      │
                    └───────────────────────────────────────┼──────┘
                                                            │
                                          ┌─────────────────▼──────────┐
                                          │    审核结果判定             │
                                          │                           │
                                          │  置信度 ≥ 85%  → 直接办结   │
                                          │  60% ≤ 置信度 < 85% → 待人工 │
                                          │  置信度 < 60%  → 待人工审核  │
                                          └───────────────────────────┘
```

### 4.2 流程步骤（15 步）

```
  ┌──────────────────────────────────────────────────────────────────┐
  │  第1步：消费者接收 MQ 消息                                         │
  │  消息体含：ticketNo, orderNo, afterSaleType, applyReason, images│
  └──────────────────────────┬───────────────────────────────────────┘
                             ▼
  ┌──────────────────────────────────────────────────────────────────┐
  │  第2步：幂等校验                                                  │
  │  查询 after_sale_order，检查 ticket_status 是否已处理             │
  │  如已处理 → 直接 ACK，不重复消费                                   │
  └──────────────────────────┬───────────────────────────────────────┘
                             ▼
  ┌──────────────────────────────────────────────────────────────────┐
  │  第3步：获取分布式锁                                              │
  │  Redis SETNX lock:order:audit:{ticketNo} TTL=30s                │
  │  获取失败 → 延迟后重试                                             │
  └──────────────────────────┬───────────────────────────────────────┘
                             ▼
  ┌──────────────────────────────────────────────────────────────────┐
  │  第4步：查询订单信息（Redis缓存优先）                                │
  │  Redis key: cache:order:{orderNo}                               │
  │  缓存未命中 → 查 MySQL order_info → 回写 Redis TTL 300s         │
  └──────────────────────────┬───────────────────────────────────────┘
                             ▼
  ┌──────────────────────────────────────────────────────────────────┐
  │  第5步：RAG 检索阶段 — 向量相似度查询                               │
  │  将 applyReason + 售后类型 拼接为 query                          │
  │  调用 Embedding 模型生成 query 向量                               │
  └──────────────────────────┬───────────────────────────────────────┘
                             ▼
  ┌──────────────────────────────────────────────────────────────────┐
  │  第6步：PgVector 相似度检索                                       │
  │  SELECT chunk_text, doc_name, similarity                         │
  │  FROM rag_chunk JOIN rag_document                                │
  │  ORDER BY embedding <=> query_embedding                          │
  │  LIMIT top_n    ← 从 system_config 读取 rag.top_n（默认3）       │
  └──────────────────────────┬───────────────────────────────────────┘
                             ▼
  ┌──────────────────────────────────────────────────────────────────┐
  │  第7步：检索结果判空                                              │
  │  如未召回任何切片（新系统刚启动无知识库）→ 直接标记为「待人工审核」      │
  │  记录失败原因：RAG知识库为空                                        │
  └──────────────────────────┬───────────────────────────────────────┘
                             ▼
  ┌──────────────────────────────────────────────────────────────────┐
  │  第8步：构建 LLM Prompt                                          │
  │  模板：                                                          │
  │  系统角色：你是电商售后审核专家，请根据以下规则对售后申请做出裁决        │
  │  参考规则：                                                      │
  │  [#1 规则原文（相似度96.8%）]                                      │
  │  [#2 规则原文（相似度91.2%）]                                      │
  │  [#3 规则原文（相似度85.7%）]                                      │
  │  用户申请：商品=[商品名] 原因=[申请原因] 类型=[售后类型]              │
  │  请输出：结论(同意/驳回/待人工) + 置信度 + 理由                     │
  └──────────────────────────┬───────────────────────────────────────┘
                             ▼
  ┌──────────────────────────────────────────────────────────────────┐
  │  第9步：调用 Ollama 大模型                                        │
  │  LangChain4j 调用 ollama.base_url 配置的模型 API                 │
  │  设置超时时间（从系统参数读取，默认 30s）                           │
  └──────────────────────────┬───────────────────────────────────────┘
                             ▼
  ┌──────────────────────────────────────────────────────────────────┐
  │  第10步：解析 LLM 返回结果                                        │
  │  期望输出格式：JSON                                               │
  │  { "conclusion": "同意退款", "confidence": 94.3,                  │
  │    "reason": "符合7天无理由退货政策...",                           │
  │    "suggestedAction": "全额退款" }                                │
  └──────────────────────────┬───────────────────────────────────────┘
                             ▼
  ┌──────────────────────────────────────────────────────────────────┐
  │  第11步：记录 AI 审核日志                                         │
  │  写入 ai_audit_log 表：LLM原始输出、RAG召回切片ID、相似度、耗时    │
  └──────────────────────────┬───────────────────────────────────────┘
                             ▼
  ┌──────────────────────────────────────────────────────────────────┐
  │  第12步：审核结果判定                                             │
  │  confidence ≥ 85% 且 conclusion≠"待人工" → AI已办结              │
  │  60%~85% 或 conclusion="待人工"       → 待人工审核                │
  │  confidence < 60% 或 LLM输出异常     → 待人工审核（标记低置信度）  │
  └──────────────────────────┬───────────────────────────────────────┘
                             ▼
  ┌──────────────────────────────────────────────────────────────────┐
  │  第13步：更新工单表                                               │
  │  UPDATE after_sale_order SET                                     │
  │    ai_audit_result=conclusion,                                    │
  │    ai_confidence=confidence,                                      │
  │    ai_audit_status=(1已办结/2待人工判定),                          │
  │    ticket_status=(1AI已办结/2待人工审核),                          │
  │    rag_rule_ids="1,5,12",                                         │
  │    ai_audit_time=NOW()                                            │
  │  WHERE id=?                                                      │
  └──────────────────────────┬───────────────────────────────────────┘
                             ▼
  ┌──────────────────────────────────────────────────────────────────┐
  │  第14步：发送延迟催单消息（仅当状态=待人工审核）                     │
  │  投递到 delayed 交换机，延迟时长=timeout.manual_review_hours     │
  │  消息体含 ticketNo，24h 后消费者检查工单是否仍为待人工审核          │
  └──────────────────────────┬───────────────────────────────────────┘
                             ▼
  ┌──────────────────────────────────────────────────────────────────┐
  │  第15步：更新 Redis 统计                                          │
  │  AI已办结 → 更新仪表盘缓存 cache:dashboard:stats                │
  │  更新 Redis 日报统计（日环比数据）                                 │
  └──────────────────────────────────────────────────────────────────┘
```

### 4.3 异常处理

| 异常场景 | 处理方式 | 是否入死信 |
|---|---|---|
| Ollama 调用超时 | 重试 3 次，间隔指数退避 | 超 3 次 → 死信 |
| LLM 返回格式无法解析 | 降级为「待人工审核」，标记低置信度 | 否 |
| RAG 检索 PgVector 连接池耗尽 | 重试 2 次，等待连接释放 | 超 2 次 → 死信 |
| Redis 分布式锁获取失败 | 延迟 100ms 重试，最多 5 次 | 否（非关键异常） |
| 工单已被人工处理（幂等） | 直接 ACK，不执行任何操作 | 否 |
| 图片凭证下载失败 | 跳过图片分析，仅基于文本审核 | 否 |

## 五、子流程③：人工审核干预

### 5.1 触发条件

工单状态为 **「待人工审核」**，运营人员打开工单详情弹窗进行处理。

### 5.2 流程步骤

```
 ┌─────────────────────────────────────────────────────────────┐
 │  运营打开工单详情弹窗                                         │
```

## 七、支撑流程⑤：RAG 知识库管理

### 7.1 完整链路

```
 ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────────┐    ┌──────────┐
 │ 管理员上传  │───>│ 存储文件   │───>│ 投递MQ    │───>│ 异步解析 &     │───>│ 向量入库   │
 │ PDF/Docx  │    │ 写入记录  │    │ doc.parse│    │ 文本切片      │    │ PgVector  │
 └──────────┘    └──────────┘    └──────────┘    └──────────────┘    └──────────┘
```

### 7.2 详细流程

```
第1步：管理员在「AI知识库管理页」点击上传文档
       · 选择文件（PDF/Word/TXT，≤20MB）
       · 选择文档分类（平台通用/数码售后/生鲜售后/历史判例）
       · 点击提交
       
第2步：后端收到请求
       · 校验文件格式和大小
       · 将文件保存到磁盘/OSS
       · 写入 rag_document 表，vectorize_status=0（待解析）
       
第3步：投递 MQ 消息到 exchange.knowledge
       · 路由键: doc.parse
       · 消息体: { docId, docCode, filePath }
       · 返回前端提示：「文档已进入异步解析向量化队列」
       
第4步：文档解析消费者消费消息
       · 根据 fileType 选择解析器：
         - PDF → Apache PDFBox / PDFBox
         - DOCX → Apache POI
         - TXT → 直接读取
       · 提取纯文本内容
       
第5步：文本切片（Chunking）
       · 按 chunk.size（默认512字符）切分文本
       · 切片策略：按段落/句子边界智能分割，避免断句
       · 每个切片记录 chunk_index 和 token_count
       · 写入 rag_chunk 表（暂不写入向量）
       
第6步：生成向量嵌入
       · 逐条调用 Embedding 模型（如 text-embedding-ada-002 或 bge-m3）
       · 生成 1536 维向量
       · UPDATE rag_chunk SET embedding = ? WHERE id = ?
       
第7步：更新文档状态
       · UPDATE rag_document SET vectorize_status=2（已向量化）, chunk_count=?
       · 处理失败 → vectorize_status=3, vectorize_error=失败原因
```

### 7.3 切片详情查看

管理员在文档列表点击「查看切片」，调用 `GET /api/knowledge/chunks/{docId}`，返回所有切片的 `chunk_index` 和 `chunk_text`，方便调试 RAG 召回精度。

### 7.4 文档重新向量化

```
管理员点击「重新向量化」
  → DELETE FROM rag_chunk WHERE doc_id = ?
  → 重新投递 MQ 消息到 doc.parse 队列（复用上传后的全流程）
  → 再次执行解析→切片→向量化
```

随着判例库不断积累，RAG 检索 SQL 扩展为：

```sql
-- 同时从规则文档和优质判例中召回
SELECT chunk_text AS content, doc_name AS source, similarity
FROM (
    SELECT chunk_text, doc_name,
           1 - (embedding <=> :query) AS similarity
    FROM rag_chunk JOIN rag_document ON rag_chunk.doc_id = rag_document.id
    WHERE rag_document.vectorize_status = 2
    
    UNION ALL
    
    SELECT case_content AS chunk_text,
           CONCAT('【判例】', case_title) AS doc_name,
           1 - (embedding <=> :query) AS similarity
    FROM quality_case
    WHERE is_active = true
) AS combined
ORDER BY similarity DESC
LIMIT :top_n;
```

### 9.1 死信来源

以下场景的消息会进入死信队列：

| 场景 | 原因示例 | 所属队列 |
|---|---|---|
| LLM 调用超时 | Ollama 模型负载过高，30s 无响应 | `queue.refund.xxx` |
| 文档解析失败 | PDF 加密/损坏，POI 无法解析 | `queue.doc.parse` |
| 向量化异常 | PgVector 连接池耗尽 | `queue.doc.parse` |
| 业务参数异常 | 用户ID为空、订单号不存在 | `queue.refund.xxx` |
| 消息重试超限 | 重试 3 次后仍失败 | 所有队列 |
| Redis 锁异常 | 分布式锁获取失败超过重试次数 | `queue.refund.xxx` |

```java
public void retryDeadLetter(Long dlqId) {
    // 1. 查询死信记录
    DeadLetterMessage dlq = deadLetterMessageDao.findById(dlqId);
    
    // 2. 更新死信状态为「已重试」
    dlq.setDlqStatus(1); // 已重试
    dlq.setLastRetryTime(new Date());
    deadLetterMessageDao.update(dlq);
    
    // 3. 根据队列名重新投递原始消息
    String originalQueue = dlq.getQueueName();
    String originalMsg = dlq.getMsgContent();
    rabbitTemplate.convertAndSend(originalQueue, originalMsg);

    operationLogDao.insert(OperationLog.builder()
        .bizType("dlq_retry")
        .bizId(dlq.getMsgId())
        .action("retry_dead_letter")
        .detail("重新投递到队列: " + originalQueue)
        .build());
}
```

### 10.2 配置读取策略

```java
@Service
public class SystemConfigService {
    
    @Autowired
    private StringRedisTemplate redisTemplate;
    
    /**
     * 读取配置：Redis 优先（TTL 30s），Miss 后查 DB 回写 Redis
     */
    public String getConfigValue(String configKey) {
        // 1. 从 Redis Hash 获取
        String value = (String) redisTemplate.opsForHash()
            .get("cache:config:all", configKey);
        
        if (value != null) {
            return value;
        }
        
        // 2. Redis Miss → 查数据库
        SystemConfig config = systemConfigDao.findByKey(configKey);
        if (config == null) {
            return null;
        }
        
        // 3. 回写 Redis（TTL 30s 防止配置更新后长时间不一致）
        redisTemplate.opsForHash().put("cache:config:all", configKey, config.getConfigValue());
        redisTemplate.expire("cache:config:all", 30, TimeUnit.SECONDS);
        
        return config.getConfigValue();
    }
}
```

## 十四、异常场景与容错策略

### 14.1 异常场景矩阵

| 场景 | 影响 | 容错策略 |
|---|---|---|
| Redis 宕机 | 限流失效、缓存Miss、排行中断 | 降级：限流跳过、查DB降级、排行显示「暂不可用」 |
| RabbitMQ 宕机 | 工单无法投递审核、文档无法解析 | 投递失败→工单标记「待重试」+ 定时任务补偿扫描 |
| PgVector 宕机 | RAG检索失败，AI审核无参考规则 | 降级：无RAG检索，LLM仅凭自身知识审核 |
| Ollama 服务不可用 | AI审核超时/失败 | MQ重试3次→死信队列→人工处理 |
| MySQL 宕机 | 全站不可用 | 兜底：Redis缓存兜底读、写操作熔断 |
| Embedding 模型超时 | 文档向量化失败 | 文档标记「向量化失败」，MQ重试 |
| 并发重复提交 | 重复工单 | 布隆过滤器 + 数据库唯一索引 + 幂等校验 |
| 大文件上传 | 内存溢出 | 限制20MB、流式处理、异步解析 |

### 14.2 熔断与降级策略总览

```
                          ┌───────────────────────┐
                          │     Sentinel 熔断器     │
                          │                       │
           ┌──────────────┼───────────────────────┼──────────────┐
           │              │                       │              │
           ▼              ▼                       ▼              ▼
    ┌────────────┐ ┌────────────┐       ┌────────────┐  ┌────────────┐
    │ Redis 降级  │ │ MQ 降级     │       │ PgVector   │  │ Ollama     │
    │            │ │            │       │ 降级       │  │ 降级       │
    │ · 限流失效  │ │ · 工单标记  │       │ · 跳过RAG   │  │ · 死信     │
    │ · 查DB     │ │   "待重试"  │       │ · LLM裸审   │  │ · 人工兜底 │
    │ · 排行不可用│ │ · 定时补偿  │       │ · 备注无规则│  │            │
    └────────────┘ └────────────┘       └────────────┘  └────────────┘
```

### 14.3 数据一致性保证

| 场景 | 方案 |
|---|---|
| 工单创建 + MQ投递 | 本地事务表 + 定时任务补偿（先写DB，再投递MQ，投递失败有补偿） |
| AI审核结果写库 | 分布式锁防并发 + 乐观锁版本号 |
| Redis排行 + MySQL数据 | Redis 数据允许短暂不一致（最终一致，每天零点全量重算） |
| 判例入库 + 知识库向量 | 异步写入，允许秒级延迟 |
| 配置修改 + 生效 | 30s TTL 最终一致，不要求强一致 |

> **总结：** 本系统以「售后工单」为核心实体，通过 **MQ 异步解耦** 保障高可用，通过 **RAG + LLM** 实现智能审核，通过 **Redis 全方位优化** 提升性能，通过 **死信运维 + 配置热加载** 保障可运维性，形成了完整的「提交 → 审核 → 处理 → 迭代」业务闭环。
